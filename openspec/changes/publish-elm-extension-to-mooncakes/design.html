Context

See proposal.md for the reason. These facts, which I measured on MoonBit 0.10.20+65efd5b93 in a scratch copy with no upload, shape the approach:

  • elm-extension-release.yml has three jobs: build (tag and vnext checks, the Wasm module, the session digest), test (the same bytes and answers on three hosts) and publish (attestation and GitHub release). No file in the repository runs moon publish.
  • moon package of moonbit/ makes _build/publish/finos-morphir-elm-<version>.zip with 326 files. It has no LICENSE, and it has tooling/*.ts, tests/*.ts, scripts/, deps.toml and moon.work.
  • exclude in moon.mod is deprecated: moon warns and names .moonignore. With a .moonignore and a LICENSE, the archive has moon.mod, README.md, LICENSE and the MoonBit packages only.
  • That archive, unpacked alone with a new MOON_HOME and MOON_WORK=off, passed 201 of 201 tests on wasm, wasm-gc, js and native.
  • Mooncakes accepts prerelease versions, and a new consumer resolved one.
  • The organization secret MOONCAKES_TOKEN is visible to finos/morphir-elm. finos/morphir-moonbit writes it into credentials.json as {"token", "username": "finos", "registry_api": "https://mooncakes.io"}, after a read-only check (GET https://mooncakes.io/api/v0/api_token/check) that the account is finos.
  • The minimum consumer compiler of the published finos modules is 0.10.20+65efd5b93, which is also the release compiler. So one compiler covers both.

Goals and non-goals

Goals: a mooncakes publication from the release tag that fails before the upload when the archive is wrong, uploads each version at most once, and proves the published version from a new consumer.

Non-goals:

  • The plan, receipt and gate machinery of finos/morphir-moonbit (scripts/mooncakes-release.mbtx). This workflow already has the tag, vnext and digest gates.
  • A pull-request or merge-queue job. The archive rules have unit tests that run in the existing bun test moonbit/tooling step.
  • The version bump to 0.5.0-preview.3, the tag and the publication. They are later steps.
  • A protected deployment environment (the maintainer chose none for now).

Decisions

REL-1. One job after publish, in the existing workflow

The job mooncakes needs build and publish, and checks out the same tag. The maintainer chose this on 2026-11-10. The tag, vnext and version checks of build stay the only gates; the job does not repeat them. Alternatives: a separate dispatch-only workflow (two places to start one release), or a job before publish (a mooncakes failure would then block the GitHub release; the maintainer preferred the GitHub release first).

REL-2. Package from a git snapshot of the tagged commit

package runs git archive <commit> moonbit into a new directory and runs moon package there. Untracked files in the checkout (.deps, .mooncakes, _build, scripts/node_modules) cannot enter the archive, and the archive does not depend on how moon reads the root .gitignore. The commit must be HEAD, and the tag must give the moon.mod version (parseReleaseTag, which the GitHub release already uses).

REL-3. Archive rules are pure and unit-tested

moonbit/tooling/mooncakes.ts holds the rules that do not need the network or moon:

FunctionRule
archiveName(version)finos-morphir-elm-<version>.zip, the name moon package writes
checkArchiveEntries(entries)requires moon.mod, README.md, LICENSE; refuses tooling/, tests/, scripts/, deps.toml, moon.work, _build/, .mooncakes/, .deps/, node_modules/, an absolute path or ..; names every bad entry
registryState(status)404 is absent, 200 is present, any other answer is unknown
isFinosAccount(status, body)200 with ok: true and username: "finos"
credentialsJson(token)the credential file content; refuses an empty token
redact(text, token)replaces every copy of the token in child output
consumerFiles(version)moon.mod, moon.work, moon.pkg and a test of the verify consumer

REL-4. A new Moon home for each check

The archive test, the upload and the consumer each use a new directory as MOON_HOME that links only bin, lib, include and share of the pinned toolchain, and each runs moon with MOON_WORK=off. No registry cache or login of the runner, and no workspace in a parent directory, can supply an input. Only the upload home ever holds a credential, and the task deletes that home when it ends.

REL-5. Stop when the version exists; upload once

Before the upload, the task reads https://mooncakes.io/api/v0/manifest/finos/morphir-elm@<version>. Only absent continues. A present version stops the job: a mooncakes version cannot change, and a new source needs a new version. The upload is one moon publish run with no retry; a failure leaves the version for a person to examine. Alternative: accept a present version whose archive checksum equals ours (as finos/morphir-moonbit does); that needs a reproducible archive and a download path, and the GitHub release step already refuses a second run of the same tag.

REL-6. The token stays in one step

Only the step Publish to mooncakes has MOONCAKES_TOKEN in its environment. The task checks the account, writes credentials.json with mode 0600 and exclusive create, runs moon publish, and removes the home in a finally block. Child output goes through redact; GitHub also masks the secret. The token goes in the check URL as a query parameter, as moon's own login does.

REL-7. The consumer checks the version that it resolved

The consumer imports finos/morphir-elm/mep. Its test requires @mep.VERSION to equal the release version and a new Session to be open. So the test fails if moon resolves another version. moon update retries with 1, 2, 4, 8, 16 and 32 seconds of wait, because the registry index can show a new version late; the tests do not retry.

The mooncakes job

# .github/workflows/elm-extension-release.yml, job mooncakes (needs: build, publish)
mise run release:elm-extension-mooncakes -- package "$RELEASE_TAG" "$RELEASE_COMMIT"   # no secret
mise run release:elm-extension-mooncakes -- publish "$VERSION"                        # MOONCAKES_TOKEN here only
mise run release:elm-extension-mooncakes -- verify "$VERSION"                         # no secret
CommandDoesFails when
packagegit snapshot, moon package, entry check, unpacked archive tested on 4 targets, zip and .sha256 into dist/elm-extension-mooncakes/tag or commit mismatch, bad entries, any test
publishchecksum check, registry check, account check, one moon publish from the unpacked archivechecksum, version present or unknown, wrong account, upload error
verifynew consumer, moon update, tests on 4 targetsversion not resolvable, any test

The job uploads dist/elm-extension-mooncakes/ as an artifact, also when it fails, so a person can read the archive that it packaged.

Risks and trade-offs

RiskMitigation
The GitHub release exists but the mooncakes job fails.The job stops before the upload for every check except the upload itself. A person reads the job and the artifact, and re-runs the failed job (the registry check stops it if the upload did happen).
The upload succeeds and verify fails.The version stays; a fix needs a new version. The job fails, so the release is visibly incomplete.
The upload path is not tested before the first real release.The moon publish step is one command on an archive that moon package already checked. The first publication of 0.5.0-preview.3 is a preview, and the maintainer approves it explicitly.
moon changes its archive name or .moonignore rules.The release pins the toolchain; checkArchiveEntries fails on a changed archive before the upload.

Migration plan

  1. Merge this change. Nothing runs until a tag.
  2. A separate PR bumps moon.mod and mep VERSION to 0.5.0-preview.3.
  3. With the maintainer's approval, push tag extension/elm/v0.5.0-preview.3 on vnext.

Rollback: remove the job. A published version cannot be removed; moon deprecate can mark it.
