Context

See proposal.md for the motivation. These facts shape the approach. Each is from finos/morphir-moonbit main at 40623b86, or from this repository.

  • The MoonBit CLI describes with ["0.2.0-draft.1", "0.1"]. When the claims name morphir.frontend.compileModel, it initializes with ["0.2.0-draft.1"] alone and a model transport offer: the ion-binary tuple first, then the morphir-json tuple, and the default limits. It uses the first agreed tuple. Otherwise it initializes on 0.1 and uses the legacy compile.
  • Its compileModel request has relative document URIs, and no sources.root, no exposedModules and no dependencies. It sends every file in one request, and refuses more than one file when the claims say multiDocument: false.
  • When a pin names a descriptor, the descriptor's claims must equal the live describe claims.
  • The Elm worker of cli2 writes classic IR (format 3). finos/morphir-ir has the migration to IR 4.0.0, and the Elm extension's parity tests already run it on morphir-elm make output.
  • The Elm classic workflow builds on Windows. mise.moonbit.toml has no Windows toolchain.

Goals and non-goals

Goals: the MoonBit CLI compiles Elm through Elm classic to an IR 4.0.0 model; the Rust CLI's 0.1 sessions do not change.

Non-goals: more than one document per compile (multiDocument stays false); package dependencies in compileModel; morphir.backend.generateModel (classic has no backend role); the ion-binary codec; IR 4.0.0 from the legacy compile (frontend.irVersions stays ["3"], which names what the legacy compile gives).

Decisions

NEG-1: Choose the version from the offer and the model transport

Initialize selects 0.2.0-draft.1 when the host offers it with a model transport offer, and otherwise 0.1 when the host offers it. A 0.2-only offer without a transport gets -32011. Describe answers any offer that names one of the two versions, with one static claim set that lists both.

Alternative: prefer 0.2 whenever it is offered, and refuse a 0.2 offer without a transport. A host that offers both and sends no transport would then fail, though it can speak 0.1. Rejected.

IR-1: Convert with finos/morphir-ir's migration, built to JavaScript and committed

moonbit/classic-ir exports classic_to_v4: read with versioned/json, migrate with migration.to_current, write with the v4 JSON writer. mise run moonbit:classic-ir builds it with moon build --target js --release and copies it to cli2/mep/generated/classic-ir.js (2 MB; 168 KB gzip in git; Bun minifies it in the executable). The Elm extension workflow, which has MoonBit, runs the task and requires no difference.

AlternativeWhy not
Port the migration to TypeScriptA second copy of the IR rules that can drift from finos/morphir-ir.
Build the converter in the classic buildThe classic workflow builds on Windows, where the MoonBit toolchain is not set up.
Make the Elm worker write v4A large change in the Elm code of morphir-elm, for one consumer.

The converter sets the attribute of each value input to its declared type before the migration, as the parity tests do: the format 3 migration refuses an input whose inferred and declared types differ, and v4 keeps no value attributes. The result then has the same form as the Elm extension's models.

MOD-1: compileModel reuses the classic compile

compileModel checks the request (tuple, language, context digest, options, package, sources), turns it into a classic compile request with irVersion "3", converts the IR and returns the envelope. The envelope, the modelId (urn:finos:morphir-elm:model: and the SHA-256 of the package name), the limits and the refusal messages are those of the Elm extension (moonbit/mep), so a host sees the same model id from either Elm frontend. Dependencies give the diagnostic elm.unsupported_dependencies, as in the Elm extension. A conversion failure is -32603: it is a defect of the extension, not of the source.

The payload must also be within the agreed maxDepth and maxNodes, counted as the MoonBit host counts them: every JSON value is a node, and the root is level 1. A larger model gives the diagnostic elm.model_limit. The Elm extension checks only the byte limits; bead morphir-ukvn.1.19 adds the same check there.

REL-1: Release 0.6.0 with the same release path

extension.json gives version 0.6.0 and mepVersions ["0.2.0-draft.1", "0.1"]. The descriptors copy capabilityClaims(), so they carry the model transport. The version-1 descriptor also lists both versions; the Rust CLI does not read that field.

Risks and trade-offs

  • [A host that rejects unknown claim members] → modelTransport is a member of claim set 0.1.0-draft.2, and the Rust CLI does not read the descriptor's mepVersions. The 0.1 initialize answer has no modelTransport.
  • [The committed converter goes stale after a finos/morphir-ir pin change] → the Elm extension workflow rebuilds it and requires no difference.
  • [moon writes different JavaScript on Linux and macOS] → the CI check would fail on the first pull request; the fix is to commit the Linux output.
  • [finos/morphir-moonbit's own qualification expects elm-classic 0.1 and format 3] → it pins v0.5.1, so it keeps passing; moving its pin to 0.6.0 is that repository's change.

Migration plan

  1. Merge to vnext after green CI; tag extension/elm-classic/v0.6.0.
  2. Verify the release: checksums, attestations, and describe plus compileModel through the MoonBit CLI with a contract 0.2.0 pin.
  3. Rollback: hosts can pin v0.5.1, which is unchanged.
