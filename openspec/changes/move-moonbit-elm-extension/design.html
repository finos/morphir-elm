Context

See proposal.md for the motivation. These facts shape the approach. Each one is from origin/main of finos/morphir-moonbit on 2026-10-30, unless the text says otherwise.

  • The code. pkgs/morphir-elm is module finos/morphir-elm 0.1.0, about 22,000 lines of MoonBit, plus 5 MB of conformance data. It has 14 commits since 2026-10-04 and no directory renames. Two scripts outside it belong to it: scripts/elm-parity-refresh.mbtx and scripts/elm-make-check.mbtx.
  • Its dependencies. It imports finos/morphir-ir, finos/morphir-sdk-spec and finos/morphir-typing. They are not on mooncakes; they resolve only through the root moon.work. Damian asked the morphir-moonbit session to publish them.
  • The host contract. The MoonBit CLI's new host (morphir-ukvn.5.64.36, host-extensions-as-workers) and its acquisition (morphir-ukvn.5.64.34, acquire-extensions-from-repositories) fix the publisher side:
    • The descriptor is release.json 2.0.0-draft.2, with runtime wasm or process.
    • A Wasm artifact has no platform. The host recognises the ABI from the module's imports (morphir-bytes-v1 or extism-kernel-v1).
    • A bundle holds the descriptor, its artifacts and one checksum per artifact, and nothing else.
    • The publish flow attests the artifacts with actions/attest@v4.
    • The host sends more than one document only to a frontend that claims multiDocument.
    • Bytes guests get 10 s per call, a 4 MiB request, a 16 MiB response and a 2 MiB decoded model payload.
    • The old core-wasm-process pin, its manifest.ion and the profile morphir/mep-bytes-v1/v1-draft are retired.
  • The existing MEP code cannot serve Elm. morphir-moonbit's finos/morphir-moonbit/mep Session takes one CompileInput document and returns a MoonBit-only type, and it refuses more than one document.
  • This repository. It already releases the JavaScript extension morphir-elm from cli2/mep on extension/elm/v* tags, with vnext as the release branch. The releases v0.1.0 to v0.4.1 exist, and finos/morphir pins v0.4.1. Its mise tasks are Bun TypeScript in .mise/tasks/, and its Bun workspace is packages/*.

Goals and non-goals

Goals:

  • The module builds and tests here without a full morphir-moonbit checkout.
  • The guest needs no host tooling from morphir-moonbit to build or test.
  • Every release is reproducible from its tag, and its bytes are the bytes that CI tested.

Non-goals:

  • Package dependencies, incremental compile and the missing SDK modules. These are follow-ups; the guest refuses dependencies explicitly.
  • A browser demo. The host change owns the browser worker.
  • morphir extension publish. It does not exist yet; the release workflow follows its documented shape so it can switch later.
  • Changes in finos/morphir-moonbit or finos/morphir.

Decisions

LAY-1. Import with history into moonbit/

Use git filter-repo on a fresh clone at a recorded commit (IMPORT_SHA):

  • keep pkgs/morphir-elm/ and scripts/elm-parity-refresh.mbtx;
  • rename them to moonbit/ and moonbit/scripts/;
  • rewrite (#N) in commit messages to (finos/morphir-moonbit#N), so GitHub does not link them to this repository's pull requests.

Merge the result with --allow-unrelated-histories. The pull request lands with a merge commit, as Damian approved.

A top-level moonbit/ keeps MoonBit away from the Bun workspace (packages/*) and from the Elm sources in src/. elm-make-check.mbtx only runs bun install and a Node script, so a Bun task replaces it.

Alternatives:

  • A one-commit copy loses the history, which is small enough to keep.
  • packages/morphir-elm-moonbit would put a MoonBit module inside the Bun workspace glob.

DEP-1. Pinned sparse checkout until the modules are published

moonbit/deps.toml records one morphir-moonbit commit and the paths needed: the three modules, plus pkgs/morphir-sdk/conformance for the mapping generator. The moonbit:deps task makes moonbit/.deps/morphir-moonbit (git-ignored) hold exactly those paths at that commit, and moonbit/moon.work lists the module paths. When the modules are on mooncakes, moon.mod uses the registry versions and the module paths leave the pin.

The publication is planned in finos/morphir-moonbit as plan bead morphir-ukvn.5.88 and open PR #275. All three modules are public in its inventory, with one shared first version, 0.1.0. A maintainer-created v0.1.0 tag starts the release workflow, which publishes with the finos mooncakes account. Consumers need stock moonc 0.10.16 or later. Task 4 (morphir-ukvn.5.88.4) records the release.

Alternatives:

  • A git submodule brings the whole monorepo and affects every JavaScript contributor.
  • Copying the modules would make a third copy that drifts.

TOOL-1. MoonBit through a mise environment

mise.moonbit.toml (used with MISE_ENV=moonbit, like the existing mise.ci-windows.toml) pins MoonBit 0.10.17+d971670cd with morphir-moonbit's http:moonbit recipe, on linux-x64, linux-arm64 and macos-arm64. JavaScript contributors install nothing new. The MoonBit tasks live in .mise/tasks/moonbit/, run moon with cwd moonbit/, and fail early with a message that names MISE_ENV=moonbit.

Alternative: MoonBit in the root mise.toml. Then every JavaScript CI job and contributor would download it.

CI-1. One pull-request workflow, two jobs

elm-extension.yml runs on pull requests to vnext that touch moonbit/**, the mise environment, the MoonBit tasks or the workflow itself.

  • test: the pin unit tests, moonbit:check (check, formatting and interfaces), and moonbit:test on four targets.
  • elm: elm make on the generated projects, and the parity refresh followed by git diff --exit-code.

Plan 2 adds a guest job to this workflow. Actions are pinned by SHA, as in the existing workflows.

GST-1. A session written for Elm in moonbit/extension

The guest has its own small MEP session. It handles describe, initialize, initialized, compileModel, generateModel, shutdown and exit, and calls the module's frontend and backend directly. It reuses the model transport encoding from finos/morphir-ir (wire and versioned JSON) so that its model payloads match what the host expects.

Alternative: make morphir-moonbit's Session generic. That is a cross-repository change on a critical path, and that session is built around one MoonBit document. We record it as a possible later convergence; the spec, not shared code, keeps the two sessions compatible.

GST-2. Build with moon and test with Bun's WebAssembly

The guest is built with moon build --target wasm --release, and handle is exported through the package's link options.

If moon cannot set a memory maximum, a small post-build step sets it to 4096 pages. That step is like morphir-moonbit's wasm-memory.mjs.

Tests instantiate the module in Bun with a host written for the test. It provides the three imports and calls handle, the same way the MoonBit CLI's worker does. A moonbit:package task writes the module and its SHA-256.

Alternative: package with morphir-moonbit's node-package-mep.mts. It writes the retired manifest.ion and depends on that repository's in-process compiler.

Plan 2 starts with a spike that proves three things: the link options, that the import list is exactly the three morphir_bytes_v1 functions with no WASI, and that a conformance project fits the host limits.

ID-1. The MoonBit extension is morphir-elm, short id elm

Damian decided this on 2026-10-30. The MoonBit CLI is the main Morphir CLI, and the MoonBit implementation is the Elm frontend it uses, so that implementation takes the plain Elm name. Its tags are extension/elm/v*, the same line as the earlier JavaScript releases. Versions go on from 0.4.1: the first release is 0.5.0-preview.1, so a host that orders morphir-elm versions never sees the new extension as older. This also matches the provider id finos/morphir-elm that the MoonBit CLI uses for the built-in frontend today.

Both extensions claim elm. A host with both installed must choose: the acquisition spec fails on ambiguity, and offers the index's recommended provider first.

Alternative: a new id, morphir-elm-moonbit, which was approved first. It would leave the plain name on the implementation that the main CLI does not use.

CLS-1. The JavaScript extension becomes Elm classic (BREAKING)

The changes:

  • cli2/mep/extension.json: id morphir-elm-classic, short id elm-classic, name Morphir Elm classic frontend, version 0.5.0.
  • Tags: parseReleaseTag already builds the tag from the short id, so classic tags become extension/elm-classic/v*.
  • File names: the archive, raw executable and descriptor names in cli2/mep/release.ts, and the executable name, become morphir-elm-classic-extension.
  • Workflows: mep-extension.yml becomes elm-classic-extension.yml, and mep-extension-release.yml becomes elm-classic-extension-release.yml, with actions/attest@v4 on the archives and raw executables. The tag filter becomes extension/elm-classic/v*.
  • Tasks: build:mep-extension becomes build:elm-classic-extension, and release:mep-extension becomes release:elm-classic-extension.
  • Internal names do not change: cli2/mep, tests-integration/mep-extension.test.ts and MORPHIR_ELM_EXTENSION_BIN.

The workflow files are renamed now, before any index registers a workflow path as the trusted signer.

Migration: the releases extension/elm/v0.1.0 to v0.4.1 stay as they are, so existing pins work. A consumer that wants a newer JavaScript release switches to the classic id, tag prefix and file names. The version jumps to 0.5.0 because the id change breaks consumers that install by id.

This rename is task group 6. It must land before the Elm extension's release workflow (group 7), because until then both workflows would start on extension/elm/v* tags.

REL-1. A single-artifact Wasm bundle

morphir-elm-0.5.0-preview.1.wasm
morphir-elm-0.5.0-preview.1.wasm.sha256
morphir-elm-0.5.0-preview.1.release.json   # published name of release.json

{
  "schemaVersion": "2.0.0-draft.2",
  "extensionId": "morphir-elm",
  "shortId": "elm",
  "version": "0.5.0-preview.1",
  "gitCommit": "<40-hex tagged commit>",
  "platformDifferences": "none",
  "artifacts": [{
    "runtime": "wasm",
    "filename": "morphir-elm-0.5.0-preview.1.wasm",
    "sha256": "<64-hex>",
    "claims": { "claimsVersion": "0.1.0-draft.2", "...": "from describe" },
    "claimCheck": "checked"
  }]
}

The release task gets claims by running describe on the built module, so the descriptor cannot drift from the guest. This replaces the provisional runtime: "core-wasm", manifest and executionProfile in the approved plan: the host specs define none of them, and the profile is retired.

No ABI member is written, because the descriptor field is not defined yet; the host recognises the ABI from the imports. The JavaScript release also publishes the descriptor as <name>.release.json, and users rename it to release.json, until morphir extension publish exists.

REL-2. Hand-rolled release in the shape of the publish command

elm-extension-release.yml runs on extension/elm/v* tags and on workflow_dispatch:

  1. build:
    • refuse a tag that is not on vnext, whose version differs from moonbit/moon.mod, whose version is not greater than 0.4.1, or that already has a GitHub release;
    • run the tests, the package task and the descriptor task;
    • run sha256sum --check;
    • upload dist/artifacts/ and the descriptor.
  2. test: run the packaged guest under Bun on Linux x64, macOS arm64 and Windows arm64. Compare the response bytes with the Linux run, and compare the digest with the build job's.
  3. publish (contents: write, id-token: write, attestations: write):
    • actions/attest@v4 with subject-path: dist/artifacts/*;
    • gh release create --verify-tag --latest=false, with --prerelease when the version has a -.

When morphir extension publish --stage/--release exists, it replaces the descriptor and upload steps, and the attest step stays between them.

REL-3. moonbit/moon.mod holds the version

The module version is the extension version, so describe, the descriptor and a later mooncakes release agree. The first release sets it to 0.5.0-preview.1 (see ID-1).

FRZ-1. Freeze the source copy

After the import lands, Elm changes are made only here. The morphir-moonbit copy gets a README note in a follow-up there, and its open parity bugs (morphir-ukvn.5.22.7.*, morphir-ukvn.5.22.3.*) gain the label repo:morphir-elm when their work moves.

Risks and trade-offs

RiskMitigation
The host's 10 s call limit, 4 MiB request or 2 MiB model payload is too small for a large Elm project.The spike measures the largest conformance project (expected IR about 990 KB JSON). If it is near a limit, raise it with the host owners under morphir-ukvn.5.64.36 before the first release.
The host does not send many documents yet.The guest claims multiDocument, and the host spec already supports that claim. Our tests use our own Bun host, so we do not wait for the CLI.
Admission may refuse a hand-rolled release, because morphir extension publish does not exist yet.Follow the documented publish shape (REL-2). Releases stay previews until the publish command exists, and the workflow switches to it then.
moon treats moonbit/.deps or moonbit/tooling as packages of the module.Task 1 checks this. If it happens, move the checkout to the repository-root .deps/.
bun install --cwd moonbit/scripts uses the root workspace and loses the Elm pins.A frozen-install check in task group 2. If it fails, the scripts package declares its own empty workspace.
Two copies drift before morphir-moonbit removes its copy.The freeze (FRZ-1), and morphir-ukvn.5.64.34.7 depends on morphir-ukvn.1.15.
A host that takes the latest morphir-elm moves from the JavaScript process extension to the Wasm extension, which does not support package dependencies yet.Elm extension releases stay previews until it reaches parity. The finos index decides recommended. The Elm classic extension stays available under its own id, and pins to v0.4.1 keep working.
Both release workflows start on extension/elm/v*.The classic rename (CLS-1, group 6) lands before the Elm extension's release workflow (group 7). A test checks that neither tag filter matches the other's tags.
Imported commits fail EasyCLA.They passed EasyCLA in finos/morphir-moonbit with the same authors. If one fails, re-import as a single commit.

Migration plan

  1. Pull request 1: import, toolchain, pin, tasks and CI (task groups 1 to 3). It lands with a merge commit.
  2. Pull request 2: the guest (task groups 4 and 5).
  3. Classic rename pull request (task group 6). It can land at any time before pull request 3. After it lands, Damian decides when to tag extension/elm-classic/v0.5.0.
  4. Pull request 3: the release workflow and docs (task group 7). Damian tags extension/elm/v0.5.0-preview.1.
  5. Follow-ups in other repositories, after approval:
    • morphir-moonbit publishes the three modules, and then this repository drops them from the pin;
    • the finos index admits the release;
    • morphir-moonbit removes its copy and the built-in registration (morphir-ukvn.5.64.34.7);
    • finos/morphir updates decision 0001 and .config/published-extension-bundles.toml to the classic name when it moves past v0.4.1;
    • morphir-moonbit's acquire-extensions-from-repositories treats its extension/elm/v0.4.1 fixture as an Elm classic release.

Rollback: each pull request is self-contained. Reverting the classic rename restores the old names; it changes no published release.

Open questions

  • Which Elm provider the finos index recommends to the MoonBit CLI. This is the index owner's call under morphir-ukvn.5.64.34; it does not change this repository's work.
  • When morphir-moonbit publishes the three modules. Until then, the pin (DEP-1) covers the gap.
